## Codebase Patterns

**`agent_versions` PROMISES eval reproducibility in its own doc comment and does NOT deliver it — a linked-skill change does not bump the agent version, so two runs tagged with the same version can be two behaviourally different agents.** `AgentRepository.update()` carries the comment "Any config change bumps the version and snapshots the new config into agent_versions (**reproducibility for eval**)" (`server/src/modules/agents/repository.ts:126-127`), and `snapshotVersion` even writes the linked `skills` ids into `config_json` (`:165-183`) — everything about it invites you to treat `(agent_id, version)` as a complete behavioural fingerprint. It is not, for three compounding reasons: (1) the bump is gated on `isConfigChange(existing, patch)` (`:137-139`), which only sees fields on the `agents` row — prompt, provider, model, strategy, output_schema, ci_fail_on, repo_intel; (2) **`setSkills` never goes through `update()` and contains zero references to `version`** (verified: `sed -n '/async setSkills/,/^  }/p' server/src/modules/agents/repository.ts | grep -c version` → `0`), so linking, unlinking, reordering, or enable-toggling a skill changes what the agent *does* while leaving its version number untouched. Worse, `snapshotVersion` has exactly **two** call sites — `create()` (`:121`) and `update()` (`:161`) — and `setSkills` is neither, so a skill re-link writes **no new snapshot at all** and version N's existing snapshot silently goes STALE against the live agent. That kills the obvious fallback ("fine, dereference `agent_versions.config_json.skills`"): the snapshot's own skill list is not trustworthy; (3) the snapshot stores skill **ids only**, never skill versions or bodies, and a skill's body edit bumps only the *skill's* own version (`server/INSIGHTS.md:111`) — so even a correct id list does not pin the skill *content* the agent ran with. Consequence for anything that compares two runs of "the same agent" (the L06 Eval Pipeline is the first consumer, `specs/2026-07-13-eval-pipeline.md`): a real behavioural regression can surface as a metric delta sitting next to an **empty system-prompt diff**, whose only available reading is "model noise". The fix is to pin the **effective** config on the run itself — prompt + provider/model + the resolved skill set **with each skill's version** — rather than referencing `(agent_id, version)`. Anyone tempted to "simplify" that back to a version pointer should read this entry first; the code comment is a trap, not a guarantee.

**Third trap in the same family, and the one nobody predicted: `setSkills` PRESERVES the live per-link `enabled`, so using it to restore a past config re-links a pinned-ENABLED skill as DISABLED.** `setSkills` is delete-then-insert and deliberately carries prior `enabled` forward (`server/src/modules/agents/repository.ts:266-281`; the reason is at `server/INSIGHTS.md:105` — a drag-reorder must not silently re-enable a skill the user turned off). That behaviour is correct for reorder and **wrong for restore**: a promote that calls `setSkills(pinnedIds)` restores the skill *set* but leaves each link's `enabled` at today's value, so a skill the measured run had ON reaches the prompt OFF — the agent is silently not the one the run measured, which is the "half-restore" AC-27 exists to forbid. A restore must therefore write the `agent_skills` rows itself, taking **both** `enabled` and `order` from the pin. Counting this one, there are now **three** independent ways the obvious promote implementation silently ships a config no eval run ever measured: the conditional bump, the snapshot-before-links ordering, and this. All three are green in any test that promotes a config differing in its *prompt* — only a skill-only promote catches them, which is exactly the case the feature exists for. Mutation-verified 2026-07-13 (`server/test/agents-promote-config.it.test.ts`).

**The sharp edge of the above, one level down: ANY "restore a past agent config" operation built on `update()` silently no-ops when the configs differ ONLY in their skills.** `isConfigChange` (`server/src/modules/agents/helpers.ts:63-74`) compares exactly eight `agents`-row fields — `name`, `description`, `provider`, `model`, `systemPrompt`, `strategy`, `ciFailOn`, `repoIntel` — and `UpdateAgent` (`repository.ts:32-43`) has **no `skills` field at all**, so skills cannot even be expressed in the patch. Therefore the natural implementation of a "promote/revert to this snapshot" feature — `update(configFields)` to bump+snapshot, then `setSkills(ids)` to re-link — produces **no version bump and no snapshot** in the one case where the snapshot differs only in its skill set, which is precisely the skill-regression scenario such a feature exists to catch. A caller that needs a guaranteed bump must own it explicitly rather than relying on `update()`'s conditional; weakening `isConfigChange` instead would change ordinary agent-update behaviour repo-wide. Found by a cross-model plan review (Gemini) reading the L06 plan against this code — worth noting that the same-family reviewers had all walked past it.

**Pulls list response is a deliberate aggregation surface — extend it instead of adding per-PR endpoints.**
`server/src/modules/pulls/routes.ts` (the `GET /repos/:id/pulls` handler around line 114) already runs two IN-queries after fetching the PR rows: one for latest-review score, one for cycle cost. When the UI needs more per-PR aggregate fields (e.g. severity_counts for the FINDINGS column added 2026-06-27), the established pattern is to add another `inArray(t.reviews.prId, prIds)` query, build a `Map<prId, …>`, and merge in the return mapper — **not** to fan out per-row from the client. The list is bounded; the extra round-trip is cheaper than N client-side fetches. Mirror any new field in `PrMeta` (`server/src/vendor/shared/contracts/platform.ts:157` AND the client copy at `client/src/vendor/shared/contracts/platform.ts:157` — they must stay in sync, see CLAUDE.md gotcha).

**`reviews.runId` has no unique index and no FK — never assume one review per run.** `server/src/db/schema/reviews.ts:19` declares `runId` as a bare nullable `uuid` column (no `.references()`, no unique constraint), so nothing in the schema prevents two review rows from carrying the same `runId`, and a stale/bad `runId` matches zero rows. `reviewByRunId` (`server/src/modules/reviews/repository/review.repo.ts:82`) therefore orders by `createdAt desc` + `.limit(1)` to pick the newest match, mirroring the newest-first convention already used by `reviewsForPull` (`review.repo.ts:58`), rather than assuming the row is unique. Contrast with `pull_requests`, which DOES have a real unique index `pr_repo_number_uq` on `(repoId, number)` (`server/src/db/schema/pulls.ts:31`), so `getPullByNumber` can rely on at-most-one-match without an explicit order-by.

## Tool & Library Notes

**`drizzle-kit` emits a BOUND-PARAMETER PLACEHOLDER for a partial index built with `eq()` — `WHERE "t"."status" = $1` — which is not valid in a migration file and will blow up at `db:migrate` time.** Hit generating `0016_*` for the L06 eval tables: `uniqueIndex('eval_drafts_case_running_uq').on(t.caseId).where(eq(t.status, 'running'))` (`server/src/db/schema/eval.ts`) round-trips through the query builder, which parameterises the literal — so the generated SQL carries a `$1` with nothing to bind it to. The fix is to bypass the builder for any partial-index predicate and write a raw template: ``.where(sql`${t.status} = 'running'`)``, which correctly inlines to `WHERE "eval_drafts"."status" = 'running'`. Partial indexes are a standard Postgres pattern (they are how you express "at most one *running* row per case" as a DB constraint rather than a race-prone read-then-write), so any future one in this repo will hit this. Versions: `drizzle-kit 0.30.1` / `drizzle-orm 0.38.3`.

**`drizzle-kit generate`'s interactive "is this column created or renamed?" prompt CANNOT be driven by piping (`yes '' | pnpm db:generate`) — it busy-loops at 100% CPU with no forward progress instead of erroring.** The CLI uses a raw-terminal prompt library, so non-TTY stdin is not a no-op, it is a hang. Any schema reshape that drops columns and adds others on the same table in one generate run (exactly what the eval-tables reshape did) will hit this prompt for every ambiguous column. Drive it with `expect` (match `-re "created or renamed"`, `send "\r"`, `exp_continue`) when it must run unattended — and check the resulting SQL actually says `ADD COLUMN`/`DROP COLUMN` rather than `RENAME`, because answering wrong silently produces a migration that *preserves* data into the wrong column.

**`knowledge.ts`'s internal declaration ORDER is load-bearing for any new Zod object that both (a) references an Agents-section enum and (b) is embedded in an Eval-section schema — and the fix is to move the embedding schema, not to reorder the enums.** These are runtime `const` initialisations, not types, so a forward reference is a TDZ `ReferenceError` at module load, not a lint nit. `Provider`/`ReviewStrategy`/`CiFailOn` are declared in `---- Agents ----` near the BOTTOM of the file, while `EvalCase` historically sat in `---- Eval ----` near the top (~`:115`) — so `EvalEffectiveConfig` (which needs `Provider` + `ReviewStrategy`) could not be declared before `EvalCase` without a cycle. L06 resolved it by moving the whole eval-case block to the file's true end (after the Agents section). Related trap in the same edit: the plan's prose put these shapes in `eval-ci.ts`, but `eval-ci.ts` imports FROM `knowledge.ts` and never the reverse — putting a schema that `EvalCase` embeds into `eval-ci.ts` would have created a genuine circular **runtime** import between the two contract files. Rule: a schema embedded by `knowledge.ts` must live in `knowledge.ts`, below every enum it references.

**A path-matching regex that includes `.`/`-` in its character class will greedily swallow trailing sentence punctuation — trim before testing a suffix condition, don't rely on `\b`.** `server/src/modules/reviews/intent-inputs.ts` (`extractPlanRefs`, the bare-path loop) matches candidate repo paths with `[\w.-]+` (needed so `specs/intent-layer.md` matches as one token), but that same class also eats a trailing sentence-ending period: `./PLAN.md.` matches whole, so `/\.md$/.test(candidate)` fails (it ends in `.md.`, not `.md`) and the plan reference silently disappears. Fix is to run the same `trimTrailingPunctuation()` (`/[),.;:!?]+$/`) used for bare URLs on path candidates too, *before* the `looksLikePlanPath` suffix check — `\b` word-boundary anchors don't help here since `.` is itself a word-adjacent non-boundary char in this class. Any future regex that mixes a "path/URL charset" including `.`/`-`/`_` with a suffix-based classifier needs this same trim-then-test order.

**A "cap" constant that's applied to one field BEFORE the overall token-budget math runs can silently override a stated priority order — the fix is to make the low-priority field's cap the only one small enough to actually bind.** `server/src/modules/reviews/intent.service.ts`'s original `classifyIntent` had `MAX_BODY_CHARS = 6000` applied to the PR body as an independent per-field cap, BEFORE `usedTokens`/`remainingTokens` were computed — so a PR body carrying an inline plan/spec past char 6000 got silently truncated, discarding exactly the content §7 of `docs/plans/intent-layer.md` says must never be truncated (plan/spec is priority #1, body #2; only hunk headers, priority #4, may be cut). Fix: raise `MAX_BODY_CHARS` to a generous safety-net-only ceiling (20_000 chars — stops a pathological multi-MB body, not a budget mechanism) and raise `TOTAL_BUDGET_TOKENS` (6000→8000); the budget math still consumes the (now much larger) capped body in full, and `truncateToApproxTokens` is applied ONLY to the hunk-header block afterward. Any future addition of a new prompt-input field with its own char cap must check whether that cap is smaller than what the priority order allows before the overall budget math runs — otherwise the "priority order" is fiction.

**Testing both a full path AND its basename against the same `RegExp[]` list lets basename-anchored and path-anchored patterns share one array with no special-casing.** `server/src/modules/reviews/smart-diff.classify.ts`'s `matchesAny` (`path:41-45`) runs every pattern in `BOILERPLATE_PATTERNS`/`WIRING_PATTERNS` against both the raw path and `basename(path)` — so `/^index\.ts$/` (must anchor to the bare filename; testing it against `src/modules/reviews/index.ts` would never match) and `/(^|\/)dist\//` (must match anywhere in the path) coexist in one list without a "basename patterns" vs "path patterns" split.

**Classifier precedence order is load-bearing, not cosmetic, when two pattern lists can both match the same file — `pnpm-lock.yaml` is a concrete collision.** `server/src/modules/reviews/smart-diff.constants.ts`'s `WIRING_PATTERNS` includes a generic `/\.ya?ml$/` catch-all (`path:75`), and `pnpm-lock.yaml` ends in `.yaml` — so if `classifyRole` (`smart-diff.classify.ts:55-59`) checked `WIRING_PATTERNS` before `BOILERPLATE_PATTERNS`, every lockfile in the repo would misclassify as wiring instead of boilerplate. Confirmed by mutation test: swapping the two `if` checks flipped `classifyRole('config/pnpm-lock.yaml')` from `'boilerplate'` to `'wiring'` and broke 3 more assertions in `buildSmartDiff`'s group-order test. Any future addition to either pattern list should re-check for this kind of cross-list collision before assuming precedence order is arbitrary.

**`@modelcontextprotocol/sdk@1.29.0`'s `McpServer.registerTool` wants a raw `ZodRawShape` for `inputSchema`/`outputSchema`, NOT a constructed `ZodObject` — pass `.shape`, not the schema itself.** Confirmed against the installed types at `server/node_modules/@modelcontextprotocol/sdk/dist/esm/server/mcp.d.ts:150-157`: `config.inputSchema`/`config.outputSchema` are typed `ZodRawShapeCompat = Record<string, AnySchema>` (`zod-compat.d.ts:5`), and the SDK internally rewraps the shape via `objectFromShape`/`normalizeObjectSchema`. `server/src/mcp/tools/list-agents.ts` passes `ListAgentsInput.shape` (empty object, since the tool takes no args) and a fresh raw shape `{ agents: z.array(Agent) }` for output — passing the `ZodObject` itself instead of `.shape` would NOT typecheck against `Args extends ZodRawShapeCompat`. The handler's success return must match `CallToolResult` (`types.d.ts:2501-2603`): `content: [{ type: 'text', text }]` (a discriminated union of text/image/audio/resource blocks) + optional `structuredContent: Record<string, unknown>` (validated at runtime against `outputSchema`); `isError?: boolean` is the failure flag (no separate error type — same envelope, `isError: true`). This is the pattern the other 4 MCP tools in this lesson (`run_agent_on_pr`, `get_findings`, `get_conventions`, `get_blast_radius`) mirror.

**`buildMcpServer(container)` (`server/src/mcp/server.ts`) is deliberately transport-agnostic — it only constructs the `McpServer` and calls the 5 `register*` fns, returning the server with no `connect()` call.** This mirrors the `buildApp()`/`server.ts` split already used for the Fastify entrypoint: transport wiring (here, `StdioServerTransport`, but a future HTTP transport is plausible) lives ONLY in `server/src/mcp.ts`, keeping `server.ts` unit-wireable (construct a `Container` with test overrides, call `buildMcpServer`, assert on registered tools — no process streams involved).

**`server/src/mcp.ts` (the stdio entrypoint) never calls `console.log` — only `console.error` — because `StdioServerTransport` owns stdout for JSON-RPC framing; any stray stdout write corrupts the wire protocol.** This entrypoint deliberately skips constructing a Fastify `app` (so Pino's default stdout transport is never instantiated in this codepath) and instead goes straight `loadConfig()` → `createDb()` → `new Container(config, db)` → `buildMcpServer(container)` → `server.connect(new StdioServerTransport())`. If a future change routes a pino-backed service through this entrypoint, its logger must be redirected to stderr explicitly — the "no bare `console.log`" rule alone won't catch a third-party logger defaulting to stdout.

## Recurring Errors & Fixes

**`pnpm typecheck` is whole-project (`tsc --noEmit -p tsconfig.json`), so a parallel MCP-tool task's `pnpm typecheck clean` acceptance criterion can show failures from SIBLING files you don't own.** During the W2-BLAST task (`server/src/mcp/tools/get-blast-radius.ts`), running `pnpm typecheck` surfaced `TS2532: Object is possibly 'undefined'` in `run-agent-on-pr.ts` and, moments later, in `get-findings.ts` — both owned by other parallel MCP-TOOLS implementers writing sibling files concurrently, unrelated to the file actually being worked on. Don't block your own task on whole-project green; instead grep the `tsc` output for your own filename (`npx tsc --noEmit -p tsconfig.json 2>&1 | grep <your-file>`) to confirm your slice is clean. Whole-project-clean is the wave-closing task's (W3-WIRE) responsibility, once all sibling files exist.

**`server/src/mcp/mappers.ts`'s `toConciseFinding`/`toDetailedFinding` must accept BOTH the raw DB `FindingRow` (camelCase, e.g. from the new `reviewByRunId` repo read) and the already-DTO-mapped `ReviewDtoFinding` (snake_case, from `ReviewService.reviewsForPull`, `service.ts:167`) — reuse `findingRowToDto` (`server/src/modules/reviews/helpers.ts:34`) inside a `normalize()` helper (`isDbFindingRow` type guard checking `'startLine' in row`) instead of re-deriving the camelCase→snake_case mapping a second time.** Two call sites in the MCP `get_findings`/`run_agent_on_pr` handlers land on genuinely different row shapes for the same logical finding, and duplicating the field mapping would drift the same way the pattern-list duplication in `smart-diff.classify.ts` did (`INSIGHTS.md:30-32`) — always check for an existing row→DTO mapper before writing a second one in a new transport layer.

**`BlastResult.factsByFile` (`server/src/modules/repo-intel/types.ts:74`, keyed by caller file: `{endpoints, crons}`) is the ONLY reliable way to attribute `impactedEndpoints`/`crons` per-changed-symbol when grouping `BlastCallerRow[]` by `viaSymbol` into `downstream[]` in `blastResultToContract` (`server/src/mcp/mappers.ts`).** `impactedEndpoints` itself is documented as a "flat union" with no per-symbol attribution (`repo-intel/types.ts:76` comment). When `factsByFile` is present, union the endpoints/crons of the files each group's callers live in (dedup via `Set`); when absent (degraded/ripgrep path, `result.degraded === true`), there's no way to attribute the flat list to a specific symbol, so the mapper puts the WHOLE flat `impactedEndpoints` list on every group rather than silently dropping it — this fallback is a judgment call (not spelled out verbatim in `docs/plans/L04-devdigest-mcp.md` §5/§6), worth reconsidering if the L04 homework implementer wants a stricter behavior (e.g. omit entirely when degraded).

**The grounding gate silently drops a Review-fixture finding whose lines don't intersect the `MockGitClient`'s injected diff hunk — an it-test seeding findings without a matching diff sees `findings: []` with no error.** `groundFindings` (`reviewer-core/src/grounding.ts:52-84`) keeps a finding only if `[start_line, end_line]` intersects a real hunk's new-side range for the same file path; `buildLineIndex` falls back to `newStart..newStart+newLines-1` from the `@@` header when the diff has no per-line map (`grounding.ts:29`). `server/test/smart-diff.it.test.ts`'s first draft passed `MockGitClient({ diff: '' })` alongside a `REVIEW_FIXTURE` finding on `src/core/handler.ts` lines 10-12 — the review ran and persisted (verdict/summary intact), but `finding_lines` came back `[]` at every downstream read (`reviewsForPull`, `GET /pulls/:id/smart-diff`), because grounding dropped the finding before persistence with zero surfaced error. Fix: the injected diff string must contain a hunk for the EXACT same file path whose new-side range covers the finding's line range — mirror the `DIFF` constant + `@@ -N,3 +N,4 @@` pattern in `server/test/intent.it.test.ts:36-42`. Any it-test seeding a `Review` fixture with non-empty `findings` MUST pair it with a matching diff, or the findings vanish silently.

**Cross-workspace 404 it-tests can't be driven by a request header — `LocalNoAuthProvider.currentWorkspace()` (`server/src/adapters/auth/local.ts:28`) always resolves to the single seeded "default" workspace, ignoring any header.** The working pattern (`server/test/agents-versions.it.test.ts:154-177`, reused in `server/test/smart-diff.it.test.ts`'s 404 test) is to insert a SEPARATE workspace row and create the PR/agent/etc under THAT workspace id, then call the route normally via `app.inject()` — the default-workspace request context simply can't see the foreign row, producing the 404 for free. Don't reach for a fake auth header; there isn't one.

**`GitClient.readFile`/`clonePathFor` (`server/src/adapters/git/simple-git.ts:129-132`, interface at `server/src/vendor/shared/adapters.ts:226-227`) do NOT sandbox against path traversal — never call `readFile` directly with an attacker-controlled path.** `SimpleGitClient.readFile(repo, path)` does a bare `join(this.clonePathFor(repo), path)` with no `resolve`/prefix check, so a path like `docs/../../../../etc/hostname` (which still passes a shape-only filter such as `intent-inputs.ts`'s `looksLikePlanPath`, since it contains `docs/`) would escape the clone dir. `intent.service.ts:118-131` (`safeResolveRepoPath`) reimplements the `resolve()` + `startsWith(rootWithSep)` + `realpath()` guard already used in `modules/conventions/service.ts:480` (`safeResolve`) rather than calling `container.git.readFile` on raw untrusted input — any future feature that resolves a PR-body-derived repo path must do the same (this pattern is now duplicated in two modules; a shared helper would be a good follow-up but neither module facing service should reach across module boundaries to share it).

**No route in this codebase used a Fastify `response:` schema before Intent Layer C2, even though `app.setSerializerCompiler(serializerCompiler)` is wired in `app.ts:66` — it's fully opt-in per route.** Every existing `routes.ts` across all modules only ever sets `schema: { params, body, querystring }`; grepping for `response:` across `modules/*/routes.ts` returns nothing pre-C2. `GET /pulls/:id/intent` (`server/src/modules/reviews/routes.ts`) is the first to add `response: { 200: PrIntentRecord.nullable() } }` — worth knowing this is a deliberate first use, not an established convention to copy blindly elsewhere without checking whether the extra runtime serialization cost/strictness is wanted on that route.

**Follow-up to the `readFile`-sandboxing entry above: the duplicated traversal guard was resolved by adding `GitClient.readFileSafe(repo, relPath): Promise<string | null>` to the port itself, not by a cross-module shared helper.** `server/src/vendor/shared/adapters.ts` + `client/src/vendor/shared/adapters.ts` (identical signature+JSDoc — diff-verified with `git diff <file> | grep '^+'` since the two files have divergent surrounding content per `INSIGHTS.md:38`'s noisy-diff warning); implemented once in `server/src/adapters/git/simple-git.ts` (`readFileSafe` + private `safeResolve`, reusing `clonePathFor`), mocked in `server/src/adapters/mocks.ts` (`MockGitClient.readFileSafe`). Both `modules/reviews/intent.service.ts` (`readRepoFile`) and `modules/conventions/service.ts` (`findConfigFiles`/`readSampleBundle`/`verifyCandidates`) now call `container.git.readFileSafe(repoRef, relPath)` instead of hand-rolling the guard — the never-throws-returns-null contract matches both modules' existing graceful-degradation callers 1:1, so no caller-side logic changed beyond swapping the call. Lesson: when two APPLICATION-layer services duplicate the same security guard against the same untrusted-input shape (repo-relative paths), and both already depend on the same INFRASTRUCTURE port, the guard belongs on the port — not a new shared module that either service would have to import sideways.

**Migrating `conventions/service.ts`'s `runExtraction` off its own `cloneRoot = await realpath(repo.clonePath)` to the port's `RepoRef`-based `readFileSafe` required keeping ONE bare `await realpath(repo.clonePath)` call (result discarded) purely to preserve fail-fast behavior.** Before the migration, a stale/missing clone directory made `realpath` throw immediately, failing the whole extraction job with a visible error. `readFileSafe` degrades to `null` per-file instead of throwing, so dropping the upfront check entirely would have silently turned a hard failure into a "No readable samples — nothing to extract" success-with-zero-results (`server/src/modules/conventions/service.ts:266-273`). Keeping the discarded-result `realpath` call preserves the original error surfacing while still eliminating the duplicated `safeResolve` traversal guard and all three raw `readFile` call sites. Any similar "replace raw fs + local guard with a port method that returns null instead of throwing" migration must check whether the ORIGINAL code relied on the exception for its own error semantics.

**`ReviewRunExecutor` was building its own `new IntentService(container, repo)` even though `ReviewService` (its only caller) already built one — two instances of the same stateless application service, from `server/src/modules/reviews/run-executor.ts:45-49` (original) and `service.ts:33-38`.** `IntentService` holds no per-instance state (just `container`/`repo` references passed straight through to every call), so it was always safe to hoist to one construction point. Fixed by adding `intentService: IntentService` as `ReviewRunExecutor`'s 4th constructor param and having `ReviewService` pass its own `this.intent` (`service.ts:39`) — no behavior change, just one fewer object graph. When a wiring review flags "N instances of the same service," check statelessness first; if stateless, injecting the caller's existing instance down through a constructor param is a pure win with no drawback.

**`MockLLMProvider` (`server/src/adapters/mocks.ts:58-67`) can only be *constructed* with `id: 'openai' | 'anthropic'`, but its `id` field type (and `ContainerOverrides.llm`'s key type) also allow `'openrouter'` — mock the `review_intent` feature's default provider by registering the instance under the `openrouter` KEY, not by trying to pass `'openrouter'` to the constructor.** E.g. `llm: { openrouter: new MockLLMProvider('openai', { structured: intentFixture }) }` — `container.llm('openrouter')` just returns whatever object sits at `overrides.llm.openrouter`; nothing anywhere checks that the object's own `.id` matches the key it's registered under, so the internal `'openai'` value is harmless. Passing `'openrouter'` as the constructor's first arg is a TS type error since the constructor param is narrower than the field it assigns.

**`classifyIntent`'s outbound `ChatMessage[]` is inspectable via `MockLLMProvider.calls[i].req.messages` — this is the only way to verify §7's token-budget priority (plan/body kept whole, only the hunk-header block truncated) without exporting a private input-builder function from `intent.service.ts`.** Split the joined user-message string at `indexOf('Changed files (hunk headers only)')`: assert no `'…(truncated — token budget)'` marker appears before that index, and one appears after, when the test constructs a large-but-under-`MAX_BODY_CHARS` body plus enough hunk headers to blow the remaining budget. See `server/test/intent.it.test.ts` ("truncates the hunk-header block before ever truncating the PR body").

**`IntentService` can be constructed and driven directly — `new Container(config, db, overrides)` + `new ReviewRepository(db)` + `new IntentService(container, repo)` — without spinning up the full Fastify app via `buildApp`/`app.inject()`.** Useful for a fast DB-round-trip assertion (`getIntent` → `null` → `repo.upsertIntent` → `getIntent` → the persisted `PrIntentRecord`) that doesn't need HTTP overhead and doesn't touch the LLM at all.

**Changing the embedding model mid-project causes pgvector queries to return zero rows silently — the column's vector dimension no longer matches the new model's output dimension.** When switching to a new embedding model (e.g. OpenAI 3-small's 1536 dims → something with 384 dims), existing vector columns in Postgres retain their old dimension constraint (`vector(1536)`). pgvector does NOT allow querying a different dimension (`SELECT * WHERE embedding <-> query_vector` silently fails when dimensions mismatch) and throws no error — the query just returns an empty result set. Root cause: the column definition is immutable at the schema level. **Must-do after changing embedding models:** (1) run a migration to recompute/reload embeddings with the new model across all tables using `vector` columns, or (2) if re-embedding is not feasible, add an explicit `ALTER TABLE t ALTER COLUMN embedding TYPE vector(new_dim)` migration BEFORE any new embeddings are stored. **Prevention:** whenever `LLMProvider` / embedding model selection changes (in `adapters/llm/`, `container.ts`, or relevant config), grep for all `vector(` column definitions in `db/schema/` and confirm the dimension in the migration matches the new model's output dimensionality. Check both `schema/` file definitions AND the last applied migration's `vector(dim)` spec (`db/migrations/000X_*.sql`).

**pgvector dimension mismatch: silent query failure with zero rows returned, no error thrown — root cause is the QUERY running against mismatched embedding space, not the column definition.** After an embedding model change, both existing vectors (old dimension) and new vectors (new dimension) physically live in the same column until a migration rewrites them. A query that sends a new-dimension vector to match against old-dimension vectors fails the distance calculation silently: the SQL `<->` operator requires both operands to have the same dimension, and when they don't, the comparison produces no matches instead of an error. This is the hardest manifestation to debug because (1) the schema shows only one `vector(dim)` definition — no hint that mismatched data exists inside, (2) queries typecheck and execute without throwing, and (3) the result is an empty set that reads as "no matching embeddings found" rather than "broken query". Confirmed in practice: switched embedding model from OpenAI 3-small (1536 dims) to a different model (768 dims), ran inserts of new embeddings (768d), then searched for existing records with a 1536d query vector (from the old embedding model) — got zero results even though embeddings existed in the DB. The issue was not "data lost" but "query dimension → old data dimension" (1536 old vectors in the column, 768 query vector tried to match against them, no match → zero rows). **Mitigation:** after confirming a migration has rewritten ALL vectors in a column to the new dimension (via `SELECT COUNT(*) FROM table WHERE embedding::text LIKE '%3836 values%'` or similar dimension-counting query), THEN verify a new-model query returns non-empty results on a row you KNOW should match (exact embedding lookup or high-score vector search). Silent failures here mean the column still has old-dimension data mixed in.
