## Codebase Patterns

**`e2e/specs/` is a naming trap: it holds browser flow *fixtures* (`*.flow.json`), not specifications.** Every other module follows "`<module>/specs/` = written specs" (`server/specs/README.md`, `client/specs/README.md`, `reviewer-core/specs/README.md` are all prose-spec remits), but `e2e/specs/` contains `01-app-boot.flow.json`, `02-repo-pulls-detail.flow.json`, `05-pr-diff.flow.json`, … — the agent-browser step definitions. Any agent or human told the general rule "single-module spec goes in `<module>/specs/`" will drop a `.md` into a directory of test fixtures. `spec-creator.md` therefore forbids `e2e/specs/` by name and routes e2e concerns to the top-level `specs/` on the reasoning that a browser flow always verifies a feature owned by another module, so it is cross-module by construction. Apply the same care to any future `<module>/specs/` rule.

**A lesson pre-scaffold can encode an EARLIER/DIFFERENT taxonomy than the final mockup — the "pre-scaffold is ~80% built and matches the spec" streak (Session Notes 2026-06-25/07-02/07-06/07-07) has an exception, and nothing flags the drift.** While authoring `specs/2026-07-10-onboarding-generator.md` (Onboarding Generator), the pre-written prompt `server/src/prompts/onboarding.system.md` was found to permit a mermaid diagram for BOTH an `architecture` AND a `routes_and_apis` section kind (with `routes_and_apis`-specific formatting rules), but the feature's fixed five-kind set from the design mockup is `architecture` / `critical_paths` / `run_locally` / `reading_path` / `first_tasks` — there is NO `routes_and_apis`. So the scaffold froze a section vocabulary the eventual design dropped. This became spec Open Question #1 (resolved: reconcile the prompt DOWN to the 5 kinds as a separate prep task in the implementation plan — a prompt-file edit, not a contract change). Lesson: when a feature's pre-built prompt/contract enumerates section kinds / enum values, diff that enumeration against the mockup's actual sections/fields BEFORE writing the spec; the pre-scaffold is a strong starting point but is NOT authoritative on taxonomy. Related: `OnboardingSection.kind` is a bare `z.string()` (a free string, NOT a Zod enum) in `server/src/vendor/shared/contracts/knowledge.ts` (~:28-47, dual-vendored), so the fixed 5-kind vocabulary must be enforced server-side, not by the contract — tightening `kind` to an enum later would be a dual-vendored two-file edit.

## Tool & Library Notes

**Attaching skills to a `.claude/agents/*.md` subagent: `skills:` preloads the body, `Skill` tool invokes on demand — they are different mechanisms.** To have a subagent load a skill's *full content* at startup, list it under the `skills:` frontmatter field (NOT by adding `Skill` to `tools`). A subagent can still invoke any other project/user skill dynamically at runtime as long as the `Skill` tool is in its `tools:` list. We use both deliberately: `planner.md:9` preloads only the two architecture skills (`onion-architecture`, `frontend-architecture`) via `skills:` so planning is grounded in real practice content, while `implementer.md` keeps `Skill` in `tools` and invokes the backend/UI skill set on demand (preloading every set would bloat context for an agent that does both UI and backend). `permissionMode: plan` (planner.md:8) makes an agent runtime-read-only — stronger than merely omitting Write/Edit from `tools`.

**Parallel implementer agents share the working tree — collision safety is by file ownership, not isolation.** `implementer.md` intentionally omits `isolation: worktree`; multiple implementers run in the same branch/checkout. The only thing preventing overwrites is the planner decomposing tasks so no two own the same file (`planner.md` task table + "Files owned" column). If you re-enable parallelism, keep task file-sets disjoint or add `isolation: worktree` back.

**A NEW standalone package that (a) consumes `@devdigest/shared` as TS source AND (b) passes those shared Zod *values* into a generic library (e.g. the MCP SDK's `registerTool`) must NOT add a `"zod"` tsconfig `paths` alias — the alias splits Zod into two type identities and makes `tsc` OOM / `TS2589`.** Discovered building `mcp-server/` (`mcp-server/tsconfig.json`). Symptom: `tsc --noEmit` ran out of heap (4 GB) with no error, or — in isolation — `error TS2589: Type instantiation is excessively deep and possibly infinite` plus `ZodArray … is not assignable to AnySchema … missing _type, _output, _input, _def` (the classic "two Zod copies" mismatch). Root cause: `@modelcontextprotocol/sdk@1.29.0`'s `registerTool` types `inputSchema`/`outputSchema` as `ZodRawShapeCompat = Record<string, AnySchema>` where `AnySchema` comes from the SDK's own resolved Zod; a `"zod": ["./node_modules/zod"]` (or `"../server/node_modules/zod"`) `paths` entry forced *my* `z` to a path `tsc` treated as a distinct module identity from the SDK's `z`, so every `z.array(Agent)` passed to `registerTool` cross-instantiated two huge Zod type graphs → runaway/OOM. `reviewer-core/tsconfig.json` HAS the `zod` alias and is fine ONLY because it imports `@devdigest/shared` as `import type` (no Zod *values* cross the SDK-generic boundary), and `server/` is fine because it has NO `zod` alias at all (single hoisted Zod identity for its code, `vendor/shared`, and the SDK). Fix: keep only the `@devdigest/shared` + `@devdigest/shared/*` path aliases, drop the `zod` one entirely — natural resolution then unifies the SDK's Zod, the package's Zod, and `vendor/shared`'s Zod at the `.pnpm/zod@<v>` realpath (verified: `mcp-server` full typecheck clean once the alias was removed). Bisect method that pinned it: probe a `registerTool` call with a *purely local* `z.object` — if it still 2589s, the alias (not the shared value) is the culprit. Also note: Vitest does NOT honor tsconfig `paths`, so the package needs a `vitest.config.ts` with `resolve.alias['@devdigest/shared'] → ../server/src/vendor/shared` (mirrors `reviewer-core/vitest.config.ts`), else value-importing tests fail with "Failed to load url @devdigest/shared".

**A blocking MCP tool (`run_agent_on_pr` in `mcp-server/`) must return in well under 60 s — the MCP *client* aborts any request after `DEFAULT_REQUEST_TIMEOUT_MSEC` (60_000 ms) with `-32001 Request timed out`, killing the call even though the server is still working.** This was the live "MCP works badly" bug: `run_agent_on_pr` bounded-polls the review up to `MAX_WAIT_MS`, whose old default was 60_000 (== the client ceiling) — a guaranteed race, and any user-set higher value (or a slow LLM) tripped `-32001` mid-review. Fix in `mcp-server/src/config.ts`: default `MAX_WAIT_MS` to 45_000 and hard-clamp it to ≤55_000 (`Math.min(wait, CLIENT_TIMEOUT_CEILING_MS)`), leaving margin for the two resolve calls + the POST that precede the poll loop; a slower review then returns the `{ run_id, status: 'running' }` handoff and the caller finishes with `get_findings(run_id)`. Verified end-to-end by driving the stdio server with an SDK `Client` (`@modelcontextprotocol/sdk/client`): `run_agent_on_pr` on a real PR returned `done` in <45 s with no `-32001`. Two separate gotchas around this that look like "MCP is broken" but aren't: (1) editing repo-root `.mcp.json` does NOT hot-reload — Claude Code only spawns the server at session start, so after re-pointing it at `mcp-server` you must restart/reload MCP before the `mcp__devdigest__*` tools exist (until then a session falls back to curl/manual `pnpm start`, which for a *stdio* server does nothing useful); (2) the server is a thin HTTP client, so it needs the API up first (`./scripts/dev.sh`) or every tool errors with the friendly `cannot reach the DevDigest API` `ApiError`.

**A subagent CAN be interactive: `AskUserQuestion` is a legal entry in its `tools:` list, so "the agent must ask the user" is NOT a reason to build a skill instead of a subagent.** `spec-creator.md:14` ships `tools: Read, Glob, Grep, Bash, WebFetch, Write, Edit, Agent, AskUserQuestion` and asks its blocking questions directly. The intuition that a subagent runs headless (it returns a final text blob to its caller, and its tool output never reaches the user's transcript) wrongly generalises to "it cannot reach the user at all" — `AskUserQuestion` surfaces in the parent UI. Practical consequence: prefer a subagent for an interactive authoring flow, since it also gets an isolated context window, a `model:` pin, and a scoped `tools:` list — none of which a main-thread skill has.

**`tools:` cannot scope `Write` to a directory — it is all-or-nothing per tool.** There is no `Write(specs/**)` syntax in agent frontmatter. Directory confinement has exactly three implementations, in ascending strength: (a) a prompt rule (`spec-creator.md` Hard rules — what we chose; the agent is human-invoked and every write is visible before approval), (b) `permissions.deny` in `.claude/settings.json` (project-wide, so it also gags `implementer`, which legitimately writes `server/**`), (c) a `PreToolUse` hook that greps `.tool_input.file_path` and exits 2 (the only unbypassable one, but it also fires project-wide and cannot see *which agent* issued the call). Note (c)'s blind spot in particular: a hook cannot distinguish a confined authoring agent from ordinary work, so "hook-enforced per-agent confinement" is not actually available. Do not promise it.

**`WebFetch` cannot read a Figma URL, and its summarizer will *execute* a fetched agent prompt rather than quote it.** Two distinct failures, both hit while building `spec-creator`. (1) Figma file URLs are auth-walled: `WebFetch` gets the SPA shell, so an agent asked to "analyse the Figma design" will confabulate one from the URL slug. `spec-creator.md` therefore instructs asking the user for a screenshot export instead. (2) `WebFetch` runs the fetched page through a small model with your `prompt` — fetching another agent's `.md` system prompt and asking for it verbatim made that model adopt the persona and reply in character ("I'm ready to help you create specifications…") instead of returning the file. Use `curl -sfL <raw-url> -o file` + `Read` for any instruction-shaped file; `WebFetch` is for prose you want summarized, not text you want quoted.

**`npm audit` cannot run in `client/`, `server/`, or `mcp-server/` — they are pnpm packages and carry only `pnpm-lock.yaml`.** Verified 2026-07-10: `cd client && npm audit --audit-level=high` exits with `npm error code ENOLOCK / audit This command requires an existing lockfile`. Use `pnpm audit --audit-level high` there. The two exceptions are `reviewer-core/` and `e2e/`, which do carry a `package-lock.json` and therefore take `npm audit` — the same split that explains why their test command is `npm test` (`reviewer-core/package-lock.json`, `e2e/package-lock.json`) while every other package is pnpm. So "pnpm only" from root `CLAUDE.md` is true of the three app packages but NOT repo-wide; any tooling that shells out to a package manager must branch on which lockfile the package actually has, rather than assuming one.
