## Codebase Patterns

**A "may not exist yet" DB-backed resource is typed `api.get<T | null>(...)`, not `api.get<T>(...)`.** `usePullDetail` (`client/src/lib/hooks/core.ts:114-120`) always has a row so it types the plain `PrDetail`. `usePrIntent` (`client/src/lib/hooks/brief.ts`) hits `GET /pulls/:id/intent`, which returns `null` before the first classification runs — typing it `api.get<PrIntentRecord | null>(...)` (not `PrIntentRecord`) lets the consuming component branch on "not computed yet" vs a loading/error state without a cast. Same shape will recur for any lazily-computed per-PR artifact (e.g. the sibling `risk_brief` feature) — check whether the GET can legitimately return `null` before assuming the non-null contract type.

## Tool & Library Notes

**`Severity` type is duplicated with different shapes — always import from `@devdigest/shared` for finding code.**
- `client/src/vendor/shared/contracts/findings.ts:11` exports `Severity = "CRITICAL" | "WARNING" | "SUGGESTION"` (3 values; the runtime finding shape).
- `client/src/vendor/ui/primitives/tokens.ts:3` exports a same-named `Severity = "CRITICAL" | "WARNING" | "SUGGESTION" | "INFO"` (4 values; UI tokens map for `SEV`/`SeverityBadge`).
- Importing the UI variant when the value comes from `FindingRecord.severity` triggers TS2322 like `Type '"INFO"' is not assignable to ...` from the consuming side and the same error inverted on producer sides. The error message points at the wrong line.
- Rule of thumb: code that reads/writes `FindingRecord` or builds `Record<Severity, …>` keyed by it must use `@devdigest/shared`'s `Severity`. UI presentation helpers that index `SEV[...]` can still use the UI type as long as they don't cross the boundary.

**`Button`'s `active` prop is styled ONLY for `kind="tertiary"` — passing `active` to a `ghost`/`secondary`/`primary` Button is a silent no-op.** `client/src/vendor/ui/primitives/Button.tsx:53-54`: only the `tertiary` kind reads `active` (`background: active ? var(--bg-hover) : transparent`); every other kind's style object ignores it. So `<Button kind="ghost" active={...}>` compiles and renders but shows NO selected state (this bit the Smart/Original order toggle in `DiffTab.tsx` — both buttons looked identical). Fix without touching the shared primitive: pass an explicit `style={selected ? {...} : undefined}` override at the call site (Button spreads `...style` LAST, `Button.tsx:77`, so it wins over the kind + hover styles) — see `DiffTab.tsx` `TOGGLE_ACTIVE_STYLE`. Only switch the button to `kind="tertiary"` instead if you also want to drop its border (tertiary has `borderColor: transparent`).

**`borderColor` and `borderWidth` are CSS SHORTHANDS (each sets all four sides), so pairing them with `borderLeftColor`/`borderLeftWidth` in the same style object triggers React's "Updating a style property during rerender … shorthand + non-shorthand" console.error — which the Next.js dev overlay surfaces as an "Issue".** `FindingCard`'s `s.card` renders a severity-colored 3px LEFT accent border (`borderLeftColor`/`borderLeftWidth`) plus the other three sides, and flips the non-left color on focus/highlight — the original code used `borderColor`/`borderWidth` (shorthands) for those three, and even had a comment claiming it was "all-longhand" (it was NOT — `borderColor` ≠ `borderTopColor`). The warning fires only when the shorthand's VALUE changes on a rerender (here, the deep-link highlight). Fix: set the three non-left sides as true longhands — `borderTop/Right/BottomColor` + `borderTop/Right/BottomWidth` — never `borderColor`/`borderWidth` alongside a `borderLeft*`. (`borderStyle: "solid"` is safe to keep as a shorthand because no `borderLeftStyle` longhand is also set.)

**jsdom does not implement `Element.prototype.scrollIntoView` — any component effect that calls it must be stubbed in the test, or the click/effect that triggers it throws.** `SmartDiffFileCard`'s "N findings" header badge scrolls the first finding line into view on click; its test sets `Element.prototype.scrollIntoView = vi.fn()` before firing the click and asserts the spy was called (`SmartDiffViewer.test.tsx`). Same applies to `FindingCard`'s deep-link expand-and-scroll. If a new interactive component scrolls, stub it per-test rather than adding a global setup (there is no shared jsdom setup file stubbing it).

## Recurring Errors & Fixes

**jsdom does not implement `Element.prototype.scrollIntoView` — any component whose effect calls `.scrollIntoView()` throws `TypeError: rootRef.current?.scrollIntoView is not a function` the moment a test mounts/rerenders it into the matching state.** The pattern already existed at `ReviewRunAccordion.tsx:54` with zero test coverage (so the gap was invisible); it resurfaced when `FindingCard.tsx`'s new deep-link effect (`targetFindingId`/`targetNonce`, mirrors the accordion) got its first test. Fix: stub it at the top of the test file before any render — `Element.prototype.scrollIntoView = vi.fn();` (`client/src/app/repos/[repoId]/pulls/[number]/_components/FindingCard/FindingCard.test.tsx`). There is no global jsdom polyfill for this in the client's vitest setup; any future test that mounts a component calling `scrollIntoView` (including a hypothetical `ReviewRunAccordion.test.tsx`) needs the same one-line stub.

## Codebase Patterns (continued)

**React Context is the correct escape hatch for threading a new prop past an intermediate component the task explicitly forbids editing.** C3 (Smart Diff deep-link, `docs/plans/smart-diff.md`) needed `FindingsPanel` (only ever rendered by `ReviewRunAccordion.tsx:157`) to receive a `targetFindingId`/`targetNonce` pair, but `ReviewRunAccordion.tsx` was out of scope ("reuse its existing `targetRunId`/`targetNonce` — do not modify it"). Solution: `FindingsTab.tsx` exports `FindingTargetContext = React.createContext<{id: string|null; nonce: number}>({id: null, nonce: 0})` and wraps its `runs.map(...)` accordion loop in `<FindingTargetContext.Provider value={{id: findingId, nonce}}>` (`FindingsTab.tsx`, around the `ReviewRunAccordion` map) — Context propagates through `ReviewRunAccordion`'s render tree regardless of what its own prop signature declares/forwards. `FindingsPanel.tsx` still declares `targetFindingId?`/`targetNonce?` as ordinary props (so it stays directly testable / usable by any future caller) but falls back to `React.useContext(FindingTargetContext)` when the real caller (`ReviewRunAccordion`) doesn't pass them: `const effectiveTargetId = targetFindingId ?? ctxTarget.id`. This dual-path kept the pre-existing `FindingsPanel.test.tsx` green with zero changes (no `Provider` needed — the context's default value is `{id: null, nonce: 0}`) while making the production deep-link work. Reach for this whenever a plan's "thread X down to component Y" instruction routes through a component you've been told not to touch.

**A confidence/visibility filter that would hide a deep-linked target must special-case that target WITHOUT touching the shared filter helper if the helper isn't in your owned-file set.** `FindingsPanel.tsx`'s `hideLow` toggle calls `visibleFindings(findings, hideLow)` (from `helpers.ts`, a file not owned by the C3 task). Rather than adding a `keepId` param to `visibleFindings` (an edit outside scope), the fix wraps the call: compute `base = visibleFindings(...)`, then if the target id isn't in `base`, prepend the original (unfiltered) finding found via `findings.find(f => f.id === effectiveTargetId)`. See `FindingsPanel.tsx`'s `shown` memo. This pattern — "call the existing helper as-is, then patch the result for one special case in the calling component" — avoids touching a shared pure-helper file for a single caller's edge case.

## Codebase Patterns (continued)

**`SectionLabel`'s `right` prop is the idiom for an inline header action — don't wrap it in a custom flex row.** `client/src/vendor/ui/primitives/SectionLabel.tsx:7-11,28` accepts `right?: React.ReactNode` and renders it `marginLeft: auto` beside the uppercase label. Already used this way at `client/src/app/repos/[repoId]/pulls/[number]/_components/FindingsTab/FindingsTab.tsx:153-158` (a muted caption) and now for `IntentCard`'s "Recompute" button (`client/src/app/repos/[repoId]/pulls/[number]/_components/IntentCard/IntentCard.tsx`, `<SectionLabel icon="Target" right={recomputeButton}>`).   run={prRuns?.find((r) => r.run_id === review.run_id) ?? null}

See `FindingsTab/FindingsTab.tsx:158` and `ReviewRunAccordion/ReviewRunAccordion.tsx:30`. The leaf stays render-only; no new hook, no duplicate fetch. Same pattern applies whenever a denormalized run-level field needs to appear on a review-level UI.

### 2026-06-29 — Skills page + custom body editor (L02)

**`Modal` renders children at zero padding — every modal body must own its `padding`. Easy to miss because the title + footer ARE padded.**
`client/src/vendor/ui/kit/Modal.tsx:60` is literally `<div style={{flex:1, overflow:auto}}>{children}</div>`. **Custom textarea with a line-number gutter is ~70 lines and zero deps — reach for it before pulling in CodeMirror/Monaco for read/edit-with-numbers UX.**
The skill body editor needed line numbers, monospace, "unsaved" indicator, and a token counter. CodeMirror is ~150KB minified, Monaco ~3MB. Use this pattern when you need "rendered like code" but **don't** need syntax highlighting, autocomplete, or multi-cursor. Cheap token approximation lives in the same file: `approxTokens(text) = max(1, round(len/4))` — good enough for a live UI counter; real tiktoken stays server-side.

**A subtitle on the left rail of a side-by-side list breaks when the column is narrow — drop it before adding `white-space: nowrap` workarounds.**
`SkillsListView` originally had a header row with `<title>+<subtitle>` block beside the search input and Add button. **A linked-skills row uses HTML5 drag-and-drop directly because `react-dnd` would be overkill — the snippet is ~6 lines and is the recurring pattern for "lightweight reorder a small list" UIs.**

### 2026-07-04 — fix circular import: FindingTargetContext moved out of FindingsTab.tsx

**A React Context created in and exported from a component file, then imported back by a descendant deeper in that same component's render subtree, is a circular module import — it survives at runtime only by luck because the context is read via a hook in the component body (evaluated at render time), not at module-eval time.** `FindingTargetContext` was originally `export const FindingTargetContext = React.createContext(...)` inside `FindingsTab.tsx` (see the "React Context is the correct escape hatch..." entry above), and `FindingsPanel.tsx` — rendered underneath `FindingsTab` via `ReviewRunAccordion` (`FindingsTab.tsx` -> `ReviewRunAccordion.tsx` -> `FindingsPanel.tsx`) — imported it straight from `../FindingsTab/FindingsTab`, closing the cycle `FindingsTab -> ReviewRunAccordion -> FindingsPanel -> FindingsTab`. Node/webpack module resolution tolerates this only because by the time `FindingsPanel`'s render function calls `React.useContext(FindingTargetContext)`, `FindingsTab`'s module has already finished evaluating and `FindingTargetContext` is a real object — a `createContext()` call used at module-eval time in the importing file (rather than inside a component body) would have thrown/returned `undefined` instead. Fix: extracted the `createContext` call + its `FindingTarget` type into a neutral module `client/src/app/repos/[repoId]/pulls/[number]/_lib/findingTarget.context.ts` (named export only) that both the provider (`FindingsTab.tsx:9`) and the consumer (`FindingsPanel.tsx:10`) import directly — neither imports the other. **General rule:** any state (context, but the same applies to enums/constants/types) consumed by more than one sibling under `_components/<Name>/` belongs in the route's `_lib/`, never defined inside one sibling's file and imported by another, even when it currently "works" — check for this shape (leaf importing from the root of its own render subtree) whenever a plan introduces a new Context for prop-drilling avoidance.

### 2026-07-04 — fix Smart-Diff badge deep-link always landing on the wrong finding

**Two ancestor/descendant components both calling `scrollIntoView` for the same click means whichever one resolves its target via an extra `useEffect + setState` round-trip will systematically lose — no `setTimeout` deferral on the "loser" fixes it, because the "winner" can be delayed by an arbitrary number of further render passes.** Clicking a per-line severity badge in `SmartDiffFileCard.tsx:163` (`onOpenFinding(f.id)`) always ended up scrolled/expanded on the SAME wrong finding in the Findings tab — the highest-severity, `defaultExpanded={i===0}` card (`FindingsPanel.tsx:88`, `helpers.ts` sorts by severity) — regardless of which badge was clicked. Two effects independently call `scrollIntoView` for one click: `FindingCard.tsx:54-61` (scrolls to the specific finding) and `ReviewRunAccordion.tsx:51-57` (scrolls to its own accordion root when `review.run_id === targetRunId`). `FindingsTab.tsx` originally resolved `findingId -> review.run_id` via a `useMemo` (`resolvedTargetRunId`) consumed by a SEPARATE `useEffect(() => setTarget(...))` — that `setState`-in-effect queues an extra React render, so `ReviewRunAccordion`'s effect (which only sees the resolved `targetRunId` on THAT later render) fires strictly after `FindingCard`'s own scroll and clobbers it every time. A first fix attempt wrapping `FindingCard`'s own `scrollIntoView` in `setTimeout(fn, 0)` did NOT work — confirmed wrong via a live browser probe (see below) showing `ReviewRunAccordion`'s scroll landing chronologically AFTER the deferred macrotask, because the extra render round-trip itself wasn't bounded to one tick. **Real fix:** eliminate the round-trip — compute `effectiveTargetRunId = resolvedTargetRunId ?? target?.runId ?? null` directly during render in `FindingsTab.tsx` instead of via effect+setState, so both scrolls resolve within the SAME commit (restoring React's child-before-parent effect ordering), THEN keep `FindingCard`'s `setTimeout(fn, 0)` defer so its more-precise scroll is still guaranteed to apply last within that single commit. General rule: when two components in the same tree both react to "scroll myself into view" for one event, derive shared target state synchronously during render wherever possible — an effect+setState hop for "resolve the target" is a race magnet against any sibling/ancestor effect keyed off a related-but-not-identical dependency.

**No `chromium-cli`/`agent-browser` available in this sandboxed dev environment, but a cached Playwright Chromium build often already exists — check before assuming browser verification is impossible.** `find ~/Library/Caches/ms-playwright` turned up `chromium-1208/chrome-mac-arm64/` (and a `chromium_headless_shell` build) left over from prior work. `npm install playwright-core@1.49.1 --no-save` (pinned to the matching driver version — a mismatched version demands `npx playwright install`, re-downloading ~300MB) plus `chromium.launch({ executablePath: <the cached binary>, args: ['--no-sandbox'] })` gets a real headless browser against the ALREADY-RUNNING local dev server with zero network installs. This was what actually falsified the first (plausible-looking, wrong) fix attempt above — `getBoundingClientRect().top` on `[data-finding-id]` elements after a real click showed the deferred scroll losing the race, which static code reading alone did not reveal.
